# 如何寫出工業級 Skill

很多人自己寫 Skill，會把背景、規則、注意事項、示例，全都塞進一個 Skill 檔案。
看起來很完整，但實際並不好用。

Skill 真正的價值在於：
當使用者提出某類需求時，Agent 能自動識別場景，載入對應流程，使用合適工具，並按固定方法完成任務。並且保證以後遇到類似任務，Agent 能夠按照流程去穩定地完成。

---

## 1. 遵守 Skill 的定義：按需載入

Skill 和 CLAUDE.md / 系統提示詞不一樣。

CLAUDE.md 更像常駐上下文。只要你在這個項目裡工作，它就會一直存在，持續影響模型行為。

Slash command 更像手動命令。使用者必須明確輸入某個命令，Agent 才知道要執行對應流程。

Skill 介於兩者之間。
它的特點是 on-demand loading：按需載入。

平時它不會把整個 SKILL.md 都塞進上下文。只有當使用者輸入和 Skill 的 description 匹配時，它才會被載入。

但有一個細節很重要：
Skill 的完整內容不是常駐的，但 Skill 的 description 會長期參與匹配。

所以 description 寫得好不好，直接決定 Skill 會不會被正確觸發。

比如一個 "生成封面圖" 的 Skill，如果 description 唯寫：
Create an image.
可能不夠。

因為使用者真實會說的是：
- 幫我做一張封面圖
- 給這篇文章配個圖
- 做一張小紅書封面
- 生成一張適合 X 長文的配圖
- 按這個標題做一張科技感海報

再比如一個 "生成 X 長文" 的 Skill，使用者不一定會說 "呼叫 article skill"。
他更可能說：
- 把這個想法展開成一篇長推
- 幫我寫一篇 X 長文
- 這個觀點能不能寫成一條長內容
- 按我的語氣擴寫一下
- 給我一個開頭更抓人的版本

這些真實表達最好寫進 description 或觸發示例裡。
否則 Skill 明明存在，卻可能不會被呼叫。

還有一種情況：如果你有很多 Skill，或者某個 Skill 本身很長，可以在 Skill 裡設定 disable，關閉自動載入，降級為 slash command。

disable 的核心意義不只是防止誤觸發，更重要的是節省 context。
因為自動觸發類 Skill 至少要讓 description 長期參與匹配。Skill 越多、description 越多，常駐的匹配成本就越高。

有些 Skill 很專業、很長、使用頻率又不高，就沒必要一直佔用資源。
比如：
- 年終總結 Skill：一年可能只用幾次。
- 簡歷重寫 Skill：找工作階段才用。
- 封面圖生成 Skill：只有做內容發佈時才用。
- 課程講義整理 Skill：只有學習某門課時才用。

這類 Skill 可以先 disable 掉。
需要時再手動呼叫。

這相當於把它從 "自動出現的工作流" 變成 "手動呼叫的工具"：
- 優點：更省 context，更少誤呼叫。
- 缺點：使用者必須記得主動叫它。

## 2. 限制 Skill 的工具邊界

Skill 可以限制允許使用哪些工具。
這不是必須的，但很有用。

因為不同 Skill 需要的權限不同。

比如在 Claude Code 裡，可以寫類似：
```
allowed-tools:
  - Bash
  - Read
  - Grep
```

如果只是整理學習資料，可能只需要：
```
allowed-tools:
  - Read
  - Grep
  - Write
```

如果是文件整理，可能只需要：
```
allowed-tools:
  - Read
  - Write
  - Grep
```

如果是封面圖生成，可能需要讀參考資料、寫出 prompt，再呼叫圖片工具：
```
allowed-tools:
  - Read
  - Write
  - ImageGenerate
```

如果是批次整理資料，才需要開放更多權限，比如：
```
allowed-tools:
  - Read
  - Write
  - Edit
  - Bash
```

核心原則很簡單：
只給完成任務所需的最小權限。

不要讓只負責生成建議的 Skill 默認能修改檔案。
不要讓唯讀分析 Skill 默認能執行任意命令。

工具越多不一定越強，有時只是風險更大。

## 3. 給 Skill 組態最適合的模型

Skill 也可以指定模型。
這點經常被忽略，但很實用。

因為不同任務對模型的要求不一樣。

寫文件、做圖、資料分析、資訊爬取、整理學習筆記、生成長文，其實不應該默認使用同一個模型。

舉幾個例子：
- 寫文件：需要表達清楚、結構穩定，可以用擅長寫作和總結的模型。
- 做圖 / 設計：需要視覺理解、佈局審美，適合多模態或設計能力更強的模型。
- 資料分析：需要穩定處理表格、解釋結果，可以用推理不錯但成本較低的模型。
- 資訊爬取：很多時候是批處理和抽取，不一定需要最強模型，便宜快的模型更合適。
- 整理學習筆記：需要分類、提煉重點、保留原意，可以用穩定便宜的模型。
- 生成 X 長文：需要結構、語氣、節奏和觀點判斷，可以用寫作能力更強的模型。
- 修改簡歷：需要理解崗位要求和表達取捨，可以用更謹慎的模型。

模型選擇不是炫技，而是成本和可靠性的平衡。
有些模型更強，但更貴。
有些模型便宜，但足夠完成簡單任務。

一個成熟的 Skill 系統，不應該所有任務都默認用同一個模型。
它應該根據任務類型選擇合適的執行模型。

## 4. 漸進式披露，限制 Skill.md 的大小

SKILL.md 不應該承載所有內容，內容太長會讓 Context 被瞬間佔滿，直接導致性能變差，思考時間變長，甚至觸發 Compact 導致失憶。

它更像入口檔案。

裡面應該放：
- 什麼時候觸發。
- 做事原則。
- 執行步驟。
- 需要哪些工具。
- 其他資料在哪裡。
- 最後怎麼驗證。

但不要把所有參考資料、長案例、指令碼、範本都塞進去。

更好的方式是分層：
```
生成封面圖/
  SKILL.md
  references/
    封面圖風格參考.md
    常見平台尺寸.md
    好壞案例對比.md
  scripts/
    檢查圖片尺寸.py
    匯出多平台版本.py
  assets/
    封面圖範本.md
    字型與配色示例.json
```

不同目錄放不同東西。
- references/ 放長文件、風格參考、平台尺寸、詳細案例。
- scripts/ 放可執行程式碼。比如檢查圖片尺寸、批次重新命名檔案、匯出多平台版本、整理表格。這些確定性操作用指令碼比讓模型每次現場生成更穩定。
- assets/ 放範本、schema、圖片、示例檔案、輸出樣式。

這樣做的好處是：
Agent 不需要每次載入所有內容。
它先讀 SKILL.md，知道整體流程。真的需要細節時，再去讀 reference，或者執行 script。

這就是 Progressive Disclosure：漸進式披露。
按需讀，按需執行。
不要一次性把所有東西都塞進上下文。

這也解釋了為什麼 SKILL.md 最好少於 500 行。
不是因為 500 行有什麼魔法，而是因為超過這個長度，通常說明你把太多東西混在一起了。

如果 Skill 太長，優先考慮三件事：
- 長說明移到 references/。
- 穩定操作寫成 scripts/。
- 範本和樣例放到 assets/。

## 5. 寫完 Skill 之後還需要驗證、打分、迭代

Skill 寫完，不代表它真的能用。
這點很重要。

如果你希望一個 Skill 更穩定，建議至少做三類驗證：
1. 能不能跑。
2. 能不能正確觸發。
3. 跑出來的結果，是否真的比不用 Skill 更好。

第三點最容易被忽略。
很多 Skill 只是 "看起來寫完了"。但它到底有沒有提升質量？有沒有減少錯誤？有沒有讓輸出更符合使用者預期？如果沒有 eval，其實沒人知道。

Claude Code 的 Skill Creator 給了一個很好的思路：Skill 不應該只靠感覺發佈，而應該配 test data、跑 eval、看結果、再迭代。

它的核心流程大概是：
1. 明確 Skill 要解決什麼任務。
2. 寫出 Skill 初稿。
3. 準備 test data/test prompts。
4. 用這些測試運行 Skill。
5. 對每個測試結果做 evaluation。
6. 給每個結果打分。
7. 根據失敗點修改 Skill。
8. 再跑一輪。
9. 直到主要測試都達到最低可接受分數。

你可以把它理解成給 Skill 寫測試。
不是單元測試那麼死，但思路類似：不要只相信 Skill 檔案本身，要看它在樣本任務裡的表現。

### 第一層：驗證它能不能跑

先測試最基礎的執行能力。

比如：
- 檔案路徑對不對？
- 工具權限夠不夠？
- 指令碼能不能執行？
- reference 能不能被讀到？
- assets 範本能不能被正確使用？
- 輸出格式是否符合預期？
- 有沒有漏掉必要步驟？

如果一個 Skill 連真實任務都跑不通，後面談觸發和質量都沒意義。

### 第二層：驗證它能不能正確觸發

自動載入類 Skill 還要測試觸發。

不能只測一句：
請運行 X 長文 skill。

因為真實使用者不會這麼說。

應該準備一組使用者真實可能會說的話：
- 把這個想法展開成一篇長推
- 幫我寫一篇 X 長文
- 這個觀點能不能寫成一條長內容
- 按我的語氣擴寫為文章

如果是封面圖 Skill，也可以測試：
- 幫我做一張封面圖
- 給這篇文章配個圖
- 按這個標題做一張科技感海報
- 做一張適合小紅書的封面

這些就是 trigger eval。

如果該觸發的不觸發，description 要補關鍵詞。
如果不該觸發的觸發了，description 要收窄邊界。

這一步最佳化的是 Skill 的入口。
入口不准，正文寫得再好也沒用。

### 第三層：準備 test data / eval cases

更關鍵的是結果質量驗證。

你需要準備 test data。

不過這不等於你要親自準備一堆測試材料。
更合理的做法是：讓 Agent 根據 Skill 的用途，自動生成第一批 test data 和 eval cases，你只需要檢查這些測試是否貼近真實場景。

比如：
- 封面圖生成 Skill：準備 5 個標題、5 種內容類型、幾張參考圖。
- X 長文 Skill：準備 5 條原始想法、目標讀者、理想成稿風格。
- 學習筆記整理 Skill：準備幾份課堂筆記、摘抄、截圖 OCR 文字。
- 簡歷重寫 Skill：準備不同崗位 JD、原始簡歷、理想修改方向。
- 週報總結 Skill：準備一週零散記錄、會議紀要、完成事項。

這裡的重點不是格式，而是思路：
你要提前定義 "什麼算好"。
否則 eval 就會變成事後憑感覺。

### 第四層：打分，不要只有主觀感受

跑完 test data 後，不要唯寫 "結果不錯"。
應該給每個 case 打分，比如 0 到 10 分。

可以用這個簡單標準：
- 0-2 分：完全沒完成任務，或方向錯了。
- 3-4 分：勉強相關，但漏掉關鍵要求。
- 5-6 分：基本可用，但還有明顯問題。
- 7-8 分：質量穩定，少量細節可改。
- 9-10 分：非常符合預期，可以作為示範輸出。

最低標準可以設成：主要 test data 至少 5 分以上。

如果某個重要 case 低於 5 分，就說明這個 Skill 還不夠穩。
尤其是高頻 Skill，這通常意味著它在某個常見場景下還不可用。

### 第五層：驗證 Skill 效果

如果想更專業，可以做 baseline 對比。
也就是同一個測試，跑兩次：
1. 不使用 Skill。
2. 使用 Skill。

然後比較結果。

Claude Code Skill Creator 的 eval 思路里，就有類似 A / B benchmark：skill-enabled vs baseline。

這很有價值。
因為一個 Skill 不只是要 "能跑"，還應該證明自己有用。

如果不用 Skill 的結果已經 7 分，用了 Skill 還是 7 分，那這個 Skill 可能沒有提供明顯增益。
如果不用 Skill 是 4 分，用了 Skill 是 8 分，這才說明它真的把經驗固化進去了。

### 第六層：根據評分改進 Skill

評分不是為了好看。
評分是為了定位該改哪裡。

常見修法有幾種：
- 觸發失敗：在 description 中增加案例。
- 誤觸發：收窄 description，加入什麼時候不觸發的描述。
- 步驟漏掉：改 SKILL.md 的步驟內容。
- 輸出格式不穩定：加輸出樣例到 assets/。
- 確定性檢查不穩定：寫 script。
- 參考資訊太長：拆到 references/。
- 工具權限不夠：補 allowed tools。
- 工具權限太大：收緊 allowed tools。
- 模型能力不夠：換更適合的 model。

然後再跑一輪 eval。

這就是 Skill 的最佳化閉環：

寫 Skill
→ 準備 test data
→ 運行 eval
→ 逐項打分
→ 找失敗原因
→ 修改 Skill
→ 再跑 eval
→ 達到最低分數線，或者至少知道它的邊界

如果是高頻、複雜、要交給別人使用的 Skill，最好跑過這個閉環。
否則它可能只是一個未經驗證的 Prompt 檔案。

## 總結：一個好 Skill 應該是什麼樣的？

一個好 Skill 不需要很玄。
它只需要做到幾件事：

- 能被正確觸發。
- 不該觸發時保持安靜。
- 工具權限足夠但不過度。
- 模型選擇符合任務成本和難度。
- SKILL.md 足夠短，資料按需展開。
- 重要 Skill 最好有 test data、有 eval、有失敗案例、有迭代。

所以寫 Skill 時，不要只問：
"我要告訴模型什麼？"

更應該問：
- 使用者說出哪些話時，這個 Skill 應該出現？
- 它出現後，應該按什麼流程做？
- 它允許用哪些工具，不允許做什麼？
- 它適合什麼模型？
- 哪些內容應該留在主檔案，哪些應該拆出去？
- 我要怎麼證明它真的有效？
- 如何不斷維護迭代讓這個 Skill 更好用？

這才是 Skill 和 Prompt 最大的區別。

Skill 並不只是單純把提示詞寫長保存下來。
它是把經驗固化成一個可觸發、可執行、可測試、可維護的工作流。
