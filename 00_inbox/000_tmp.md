## 資料庫如何儲存/獲取資料

- **最簡單的 Bash 資料庫資料結構**

    ```bash
    #!/bin/bash
    ## $1 是鍵 (key)，$2 是值 (value)
    
    ## 使用 >> 將鍵值對附加到資料庫檔案
    ## 我們使用 `,` 來分隔鍵和值
    db_set () {
      echo "$1,$2" >> database
    }
    
    ## 使用 grep 獲取資料庫中的行
    ## 然後透過 pipe 使用 sed 將鍵替換為空字串（因為我們只需要值）
    ## 最後我們只需要獲取一個結果
    db_get () {
      grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
    }
    ```

    - 執行 `db_set key value` 將鍵值對儲存到 `database` 檔案中。
    - 使用 `db_get key` 獲取值。
    - 值可以是 JSON 格式：

        ```bash
        > db_set 123456 '{"name":"London","attractions":["Big Ben","London Eye"]}' 
        
        > db_set 42 '{"name":"San Francisco","attractions":["Golden Gate Bridge"]}'
        
        > db_get 42
        {"name":"San Francisco","attractions":["Golden Gate Bridge"]}
        ```

    - 簡單地使用 `,` 分隔鍵和值。
    - 透過新增一行來插入新記錄：

        ```jsx
        > db_set 42 '{"name":"San Francisco","attractions":["Exploratorium"]}' 
        
        > db_get 42
        {"name":"San Francisco","attractions":["Exploratorium"]}
        
        > cat database
        123456,{"name":"London","attractions":["Big Ben","London Eye"]}
        42,{"name":"San Francisco","attractions":["Golden Gate Bridge"]}
        42,{"name":"San Francisco","attractions":["Exploratorium"]}
        ```

    - **這就是日誌結構 (log structured)！**
    - 當我們在這裡說「日誌 (log)」時：
        - 我們不是特指「應用程式日誌 (application log)」。
        - 我們指的是「**僅附加的記錄序列 (an append-only sequence of record)**」，可以是人類可讀或二進位格式。
    - 問題是當這個日誌變得很大時...
        - 查找一個鍵需要掃描所有內容，時間複雜度為 $O(N)$。
        - 這裡我們需要一個**索引 (index)** 資料結構來幫助：
            - 假設我們有一個 B 樹 (B-tree) 幫助我們，時間複雜度變為 $O(\log N)$。
            - 索引是**衍生資料 (derived data)**，它有助於提高查詢速度，但代價是寫入速度變慢和空間增加。
    - 「真實」的資料庫還需要處理**併發寫入 (concurrent write)**、**崩潰恢復 (crash recovery)**、**清理 (clean up)**（避免耗盡磁碟空間）等問題。

- **雜湊索引 (Hash Index)**
    - 使用**記憶體內雜湊表 (in-memory hashmap)** 來記錄鍵值對：
        - **鍵 (key)** 是使用者定義的鍵。
        - **值 (value)** 是指標可以跳轉到的**位元組偏移量 (offset in byte)**。
        - 查找鍵 42？
            - 記憶體內雜湊表返回 64。
            - 我們可以從檔案的第 64 個位元組偏移量開始讀取並獲取值。
        - 例如：Riak 的 Bitcask。
    - **如果磁碟空間不足怎麼辦？**
        - 我們可以為每個檔案配置一個最大大小。
        - 當檔案達到最大大小時，建立並記錄到第二個檔案。
        - 我們還可以執行**背景程序**進行**壓縮 (compaction)** 以節省空間：例如，我們只保留鍵的最新值。
        - 在壓縮過程中也可以合併多個檔案。
        - 當我需要查找時，我從最新的雜湊表/檔案開始搜索。
    - **需要考慮的一些問題：**
        - 使用二進位格式可以節省更多空間並降低時間複雜度。
        - 在壓縮過程中，使用**刪除標記 (tombstone)** 來標記可以移除的鍵。
        - 定期執行**快照 (snapshot)**，這樣當我們需要執行崩潰恢復時，就不需要從頭開始。
        - 需要一些**校驗和 (checksum)** 機制來檢測資料庫崩潰時發生的部分寫入/結果。
        - 一個寫入執行緒和多個讀取執行緒。
    - **順序僅附加 (sequential append-only) 的優勢是什麼？** 我們有了雜湊表，為什麼不直接使用鍵來更新值呢？
        - 順序寫入的優勢：
            - 比硬碟中的**隨機尋找 (random seek)** 快得多（在 SSD 中也稍快）。
            - 更容易**並行 (parallel)** 運行，隨機寫入難以並行 → 並行運行也能提高速度。
            - 易於進行崩潰恢復。
            - 易於合併。
    - **缺點？**
        - 雜湊表需要放入**記憶體**中。
        - 進行**鍵的範圍搜索 (range search for key)** 效率低下（為什麼？）。

- **SST 和 LSM 樹 (Log Structured Merge)**
    - LSM 樹用於 *Bitcask、LevelDB、Google BigTable、RockDB、Cassandra（專注於寫入效能，多為 NoSQL）*。
    - **什麼是排序字串表 (Sorted String Table, SST)？**
        - 基於雜湊索引的概念，僅附加。
        - 但這次，我們將使**鍵排序且唯一**。
            - 這會使寫入變慢，但帶來以下優勢。
        - 由於它是排序的，因此非常容易壓縮，如下所示：
            - 就像我們進行**合併排序 (merge sort)** 一樣，先排序再合併。
        - 您**不需要**將所有索引都放入記憶體中：
            - 您可以擁有**稀疏鍵 (sparse key)**，並且只需要將稀疏鍵放入記憶體中。
            - 例如，無需將 `handiwork` 放入記憶體中，要獲取 `handiwork`，從 `handbag` 開始查找 → `102134` 處找到它。
            - 此外，偏移量（上圖灰色區域）可以被壓縮，只有在需要掃描時才需要解壓縮。
    - **如何建立和維護 SST？**（也稱為**日誌結構合併樹 (Log-Structured Merge Tree) 演算法**）
        - **如何排序？**
        - 記憶體內使用 **AVL 樹** 或**紅黑樹 (black-red-tree)**，磁碟上使用 **B 樹**。
        - 當您寫入時，先寫入**記憶體 (memtable)**。
        - 當 `memtable` 大小超過給定閾值時，儲存到磁碟。
        - 當您讀取時，先檢查 `memtable`，如果找不到，則搜索**最新的磁碟區段 (disk segment)**，然後繼續搜索到最不新的區段。
        - 背景程序運行合併和壓縮過程。
        - 使用**日誌 (log)** 進行崩潰恢復，儲存到磁碟後即可移除此日誌。
        - LevelDB、RocksDB 將此用於其鍵值儲存，Cassandra 和 Hbase 在其儲存過程中也使用類似的邏輯。
    - **優化：**
        - 如果找不到鍵，成本很高（先檢查 `memtable`、最近的磁碟區段，然後一直到所有區段）→ 先使用 **布隆過濾器 (bloom filter)** 檢查鍵是否存在。
        - **壓縮優化：**
            - **大小分層 (size-tiered)：** 將小型且新的 SSTable 合併到舊且更大的 SSTable 中。
            - **分級 (leveled)：** 我們假設對新資料的查詢更多，因此新資料進入更薄的 SSTable，並根據新近程度分為多個級別。

- **B 樹 (B-tree)**
    - 廣泛用於許多資料庫（主要是 RDBMS、MySQL、PostgreSQL、CouchDB 等）。
    - 將資料放入一個區段（4KB），一個**頁面 (page)**。
        - 4KB，類似於檔案系統區塊，這是為了與檔案系統對齊，以減少頁面重新獲取。
    - 每個頁面都有**鍵 (keys)** 和指向**子頁面 (children pages)** 的**指標 (ptrs)**。
        - **查找：**
            - 要查找 `userId 251`，首先找到 200~300 之間的指標。
            - 然後該指標轉到子頁面，找到 250~270 之間的指標。
            - 然後找到 251 的值。
            - 值儲存在**葉子頁面 (leaf page)** 中。
        - **分支因子 (branching factor)：**
            - 每個頁面中指標/引用的比率。
            - 通常我們有數百個指標/引用。
        - **更新：**
            - 像查找一樣，找到它並更新其值。
    - **新增鍵：**
        - 找到包含此新值的範圍。
        - 如果空間不足，則**分裂 (split)** 成兩個頁面。
    - **自我平衡 (self-balance)：**
        - 因此 $n$ 個鍵將有 $\log(n)$ 的樹高！在大多數情況下通常是 3-4 層深。
        - 4KB 頁面和 4 層深可以包含 256 TB 的資料。
    - **寫入**所需的**操作 (ops)** 比 LSM 更多，因此比 LSM 慢：
        - LSM 寫入只是附加一條新記錄。
        - B 樹是**原地修改 (modify in place)**，因此它需要先尋找到該位置（在磁碟中）並進行修改。
        - 這也涉及自我平衡的**分裂頁面操作**，因此我們一次有多個操作。
    - **如果資料庫在中間崩潰或斷電：**
        - 我們可以使用 **預寫式日誌 (write-ahead log, WAL)**（僅附加）在寫入之前記錄此操作，並可以使用它進行恢復。
        - 有時我們也使用**閂鎖 (latches)**（輕量級鎖）來允許 B 樹的並行操作。

- **B 樹 vs LSM 樹**
    - **用途：**
        - B 樹：大多數 RDBMS。
        - LSM：許多 NoSQL 使用它。
    - **讀取：**
        - B 樹：讀取速度更快，只需要較少的層級即可查找。
        - LSM：與 B 樹相比可能較慢，但取決於情況。
    - **寫入：**
        - LSM：
            - 通常寫入速度比 B 樹快，因為它只是**附加日誌**。
            - 附加日誌是**順序寫入**。順序寫入對於硬碟存取具有良好的效能至關重要。
            - 在某些情況下，如果寫入吞吐量過高，導致壓縮過程跟不上，這將影響寫入結果。
        - B 樹：
            - B 樹需要寫入 WAL 和樹頁面。
            - 可能需要分裂頁面、建立節點或重新平衡。
            - 寫入速度比 LSM 慢。
    - **可預測的查詢延遲：**
        - B 樹：具有**更可預測**的查詢延遲。
        - LSM：查詢可能在 LSM 樹運行壓縮時到來，這會影響讀取效能並使查詢**不可預測**。
    - **空間：**
        - LSM：由於其壓縮，**空間節省**效果好。
        - B 樹：使用頁面，有時會出現**頁面碎片化 (page framentation)** 問題（頁面中的某些空間未被使用）。

- **其他資料結構**
    - 到目前為止，我們只討論了**主鍵 (pk)**，它是表中的一行、文件資料庫中的一個文件、圖形中的一個頂點。
    - **次級索引 (Secondary Index)**
        - 如果我們可以在這些表（地區表、職位表、教育表）中為 `user_id` 建立次級索引，我們就可以在這些表中找到這些行。
        - 次級索引的問題是**值不是唯一**的，如何處理？
            - 讓值成為匹配行的**列表**。
            - 在條目中添加一個**行識別符 (row-identify)** 使其唯一。
        - B 樹或 LSM 樹都可以設定次級索引。
    - **放置索引值的兩個位置：**
        - 我們可以將**實際資料**放入值中。
        - 或者我們可以將**指標/引用**放入值中：
            - 實際資料位於**堆檔案 (heap file)** 中（可以僅附加或覆寫）。
            - 好處是次級索引引用此記錄，可以使用此引用，無需複製多份實際資料。
            - 要更新一個值，如果新資料較小，則直接覆寫；如果較大，我們需要找到其他位置放置或使用另一個指標幫助我們轉到另一個位置。
            - 有時，轉到指標的開銷太大，我們可以將所有資料放入索引中，稱為**聚簇索引 (clustered idx)**。
            - 一種變體稱為「**包含欄位的索引 (idx with included cols)**」或「**覆蓋索引 (covering idx)**」，它將最常查詢的資料放入索引中。
            - **缺點：** 使用更多空間來儲存索引。
    - **多欄位索引 (Multi-col idx)**
        - 也稱為「**串聯索引 (concatenated idx)**」。
        - 例如，新增一個索引 `(firstname, lastname)`，您可以使用此索引查找具有特定名字和姓氏的人。
    - **多維索引 (Mult-dim idx)**
        - 假設您需要一個資料庫來搜索餐廳位置：

            ```jsx
            SELECT * FROM restaurants 
            WHERE latitude > 51.4946 AND latitude < 51.5079 
            	AND longitude > -0.1162 AND longitude < -0.1004;
            ```

        - B 樹和 LSM 樹無法很好地處理這個問題，它們不能對兩個鍵進行範圍搜索。
        - **解決方案？**
            - 使用**空間填充曲線 (space-filling curve)** 將 2D 轉換為單個數字，然後使用普通索引。
            - 使用**空間索引 (spatial idx)**，例如 **R 樹 (R-tree)**。
        - **其他應用？** 查找相似顏色（R、G、B），任何 2D 資料，例如（時間、溫度），使您能夠查找 2013/2/1~2013/2/39 之間且溫度在 20~23 度之間的資料。
    - **全文搜索和模糊搜索 (Full-text search and fuzzy search)**
        - 像 Lucene 這樣的工具可以幫助您查找編輯距離 (edit-dist) 為 1 的單詞（您可以拼錯一個單詞，但仍然可以找到它，就像 Google 搜索一樣）。
        - **如何做到？** 使用類似 SSTable 的儲存和索引作為**有限自動機 (finitie automate machine)**，並可以轉換為 **Levenshtein 自動機 (Levenshtein automaton)** 以實現編輯距離搜索。
    - **儲存到記憶體 (Save into memory)**
        - 到目前為止，我們主要討論儲存到磁碟。為什麼？磁碟更便宜，斷電後資料不會丟失。
        - 隨著技術進步，記憶體隨著時間的推移變得越來越便宜。
        - 我們有 **記憶體內資料庫 (in-memory db)**，如 Memcached 和 Redis。
            - 也可以透過電池供電的記憶體、將變更日誌儲存到磁碟、將快照儲存到磁碟、將記憶體儲存到其他機器來支援**持久儲存 (persistet save)**。
            - 然後記憶體內資料庫在啟動時可以從上述位置載入。
            - 可以支援更多和更複雜的資料結構（優先佇列、集合），因為在記憶體中更容易實現。

- **OLTP 和 OLAP**
    - **OLTP (Online Transaction Processing)：** 交易操作，查詢結果不多，需要覆寫記錄。
    - **OLAP (Online Analytical Processing)：** 掃描大量記錄，有時專注於關鍵欄位，使用統計、聚合、求和，例如今年香蕉的銷量。

    | 屬性 (props) | OLTP | OLAP |
    | :--- | :--- | :--- |
    | 讀取模式 | 透過鍵查詢少量記錄 | 透過大量資料進行聚合 |
    | 寫入模式 | 隨機存取，需要低延遲寫入 | 批量匯入或事件串流 |
    | 主要使用者 | 應用程式使用者、終端使用者 | 內部資料分析師 |
    | 資料 | 最新資料 | 歷史資料 |
    | 資料量 | GB~TB | TB~PB |

    - 如果您的資料不多，您的資料庫可以同時處理這兩者；如果您的資料量變大，則需要引入**資料倉儲 (Data warehouse)**。

- **資料倉儲 (Data warehouse)**
    - 資料倉儲中的 OLAP，因此大量的掃描和載入資料不會影響需要低延遲的事務處理。
    - 定期複製 OLTP 資料，或從 OLTP 串流資料，轉換為合適的模式並載入到倉儲中，這稱為 **擷取-轉換-載入 (Extract-Transform-Load, ETL)**。
    - **星型和雪花型綱要 (Star and Snowflake Scheme)**
        - 如下圖所示，中心是**事實表 (fact_table)**。
        - 事實表中的某些欄位是必需的屬性，某些欄位是引用其他表（我們稱之為**維度表 (dimensional table)**）的**外鍵 (foreign key)**。
        - 有了這個維度表，我們可以在需要時使用連接 (join) 來修飾我們的查詢。
        - 為什麼叫**星型綱要 (star scheme)**？這是因為事實表位於中心，其他維度表圍繞在周圍。
        - 我們可以有更多的維度，使其看起來像**雪花 (snowflake)**。

- **欄式儲存 (Col store)**
    - 如何優化包含數十億級資料、PB 級的事實表？
    - 事實表將有 100 多個欄位，有時我們只需要 4~5 個欄位進行查詢。
    - 例如，我們透過連接和過濾從維度表中獲取大量行，最後我們只需要獲取 3 個欄位：

        ```jsx
        SELECT
          dim_date.weekday,
          dim_product.category,
          SUM(fact_sales.quantity) AS quantity_sold
        FROM fact_sales
          JOIN dim_date ON fact_sales.date_key = dim_date.date_key
          JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk
        WHERE
          dim_date.year = 2013 AND
          dim_product.category IN ('Fresh fruit', 'Candy')
        GROUP BY
          dim_date.weekday, dim_product.category;
        ```

    - **如果我們將每個欄位儲存在自己的檔案中呢？** 如下所示：
        - 您只需要將所需的欄位組合成一行即可獲得最終的行。
    - **如何壓縮欄式儲存？**
        - 通常，我們會有數十億條記錄，但只有數萬種產品，我們有很多稀疏值，使用**位元圖編碼 (bitmap encoding)** 進行壓縮，由於有這麼多零，我們可以再次使用**遊程編碼 (run-length encoding)** 進行壓縮。
        - 對於以下情況，我們只需要獲取這 3 個值並進行 **OR** 運算：
            `WHERE product_sk IN(30,68,69)`
        - 對於這個情況，獲取兩個值並使用 **AND** 運算：
            `WHERE product_sk = 31 AND store_sk = 3`
        - 我們甚至可以對欄式儲存中的欄位進行**排序**，這有利於壓縮。
        - 順帶一提，我們需要以**相同的方式**對所有欄位檔案進行排序（這樣我們才能最終將它們正確地組合成行），例如我們可以按 `dateTime` 排序，以便有效地使用 `WHERE=dataTime` 查詢。
