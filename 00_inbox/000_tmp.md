- 為什麼我們想複寫 (replicate)？
    - 備份 (backup)
        - 一個節點當機，我們有其他節點可以還原 (restore)。
    - 地理位置 (geo-locate)
        - 低延遲 (low latency)，節點就在台灣（對我來說，甚至在 ISP 快取中）。
    - 高可用性 (high avail)
        - 因為您可以容忍節點故障。
    - 高吞吐量 (high throughput)
        - 假設您解決了熱點 (hot-spot) 問題。
        - 這樣 1000 個請求會分別進入每個節點，每個節點可以處理 100 個請求。
        - 沒有在佇列中等待。
        - 就像您可以處理 1000 個請求而無需等待一樣。
- 實作複寫日誌的 4 種方式：
    - 基於語句 (statement-based)
        - 很少使用，因為有以下問題：
            - 非確定性操作 (non-deterministic op)
                - 像語句中的 $\text{RAND()}$、$\text{NOW()}$。
            - 如果語句依賴於資料
                - 像 auto-increment 或交易 (transaction)。
                - 所以您需要確保複寫是**依序**執行的 (sequentially)。
                    - 不能平行執行 (in parallel)。
            - 無法複寫具有副作用 (side effect) 的語句。
    - WAL (寫入前日誌, write ahead log)
        - 使用 **SSTables**，背景執行日誌壓縮 (log compaction)。
        - 優點：參見 SSTable 部分。
        - 缺點：
            - SSTable 是一種儲存引擎（關於哪些位元組進入哪個硬碟扇區的細節）。
            - 這意味著不同版本或主動和被動伺服器之間的異質性可能與這種儲存方式不相容。
            - 這意味著您需要所有伺服器都支援這種實作方式。
            - 這可能會在未來造成相容性問題。
    - 基於行 (Row-based replication)
        - 與 WAL 相比，將複本與儲存引擎解耦 (decouple)。
        - 日誌只需要記錄：
            - 新增行的所有欄位 (col) 資訊。
            - 被刪除行的主鍵 (pk)。
            - 更新行的主鍵和修改的欄位。
        - 被動和主動節點可以使用不同的版本，並且可以很好地與異質的下游系統（如變更資料擷取, change data capture）協同工作。
    - 基於觸發器 (trigger-based)
        - 以上方法是在資料庫層級完成的，這是應用程式層級的。
        - 應用程式會非常靈活（您可以做任何語言能做的事）。
        - 使用外部工具，如 Oracle Golden Gate 或資料庫內建的觸發器或儲存程序。
            - 例如：假設您有一個寫入，這是一個觸發處理程序進行複寫的事件。
        - 然而，由於我們在應用程式層級處理...
            - 較高的額外開銷（往返、頻寬、記憶體和維護）。
            - 容易出錯。
        - 如果您的案例需要，不應該將其設為預設選項。
        
- 領導者-追隨者複寫 (leader-follower in replication)
    - 也稱為主動/被動 (master/slave)。
        - 寫入主動節點 (active) 並複寫到追隨者 (follower)。
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/48d59b09-2151-428e-94a1-e9d5708d8e45/Untitled.png)
            
        - 非同步 (async) vs 同步 (sync)。
            - follower1 是同步的。
                - 只有當 user1234 收到來自 follower1 的確認後，整個處理才算完成。
                - 類似請求-回應模型 (req-response model)。
            - follower2 是非同步的。
                - 不需要收到確認。
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/e0d265e2-5336-4ba0-ace1-f470c9fc76d4/Untitled.png)
            
            - 同步 (sync) 意味著只有在複寫完成（到被動節點）後才向客戶端回應 200。
                - 優點：
                    - 確保複寫完成，並且當使用者查詢時，資料是同步的。
                - 缺點：
                    - 較慢（需要等待同步完成）。
                - 但是，如果我們有很多被動節點，我們是否需要等待所有被動節點的同步？
                    - 如果一個被動節點當機了怎麼辦？
                        - 解決方案：只需要等待 1 個或等待一定數量的被動節點完成即可，也稱為：半同步 (semi-synchronous)。
            - 非同步 (async)：
                - 優點：
                    - 不需要等待同步並回應客戶端 200 $\rightarrow$ 快速。
                - 缺點？
                    - 如果主動節點在複寫前當機，資料丟失。
    - 如何設定新的被動節點？
        - 獲取主動節點的快照並將其複製到新的被動節點。
        - 然後被動節點使用主動節點的日誌來獲取快照之後的活動。
    - 如何處理節點當機？
        - 被動節點當機：
            - 較容易。
            - 知道失敗的被動節點的最後一個交易，並從主節點恢復（從日誌中獲取資料）。
        - 主動節點當機：
            - 比較棘手。
            - 這個過程稱為**故障轉移 (fail-over)**。
                - 我們需要提升一個新的被動節點成為主動節點。
                - 需要重新配置，讓所有其他被動節點知道新的主動節點。
                - 需要處理舊的主動節點返回時，且舊的主動節點已不再是主動節點的情況。
            - 使用超時 (timeout) 來確認被動節點是否當機，但設定這個超時很棘手。
            - 如何提升被動節點成為主動節點？
                - 使用共識演算法/投票。
            - 如果舊的主動節點上有一些資料尚未傳遞給任何其他被動節點，當一個被動節點提升為新的主動節點時，該怎麼辦？
                - 如何處理那些衝突資料？
                    - 丟棄它們？可以，但違反了持久性。
                - 一個案例研究：
                    - Github 曾發生過一個案例，一個新的主動節點被提升了。
                    - 這個新的主動節點使用了舊的主動節點已經用過的 auto-increment 計數器。
                    - 然後外部的 Redis 使用了那個舊的計數器。
                    - 所以基本上，Redis 連接到錯誤的節點去獲取資料並返回給使用者！
                    - 從使用者的角度來看，就像您獲取了別人的儲存庫 (repo) 資料一樣。
            - 如果舊的主動節點返回並認為自己也是主動節點，我們就會出現腦裂問題，導致資料衝突。
                - 稍後會討論更多。
            - 許多團隊手動進行故障轉移 $\rightarrow$ 是因為上述的複雜性。
        
- 複寫延遲問題 (replication lag problem)
    - 如前所述，同步複寫很難使用。
    - 所以大多數情況下我們使用非同步複寫。
    - 非同步 $\rightarrow$ 導致最終一致性問題。
    - 以下是一些保證以確保避免異常情況：
    - 讀取您自己的寫入保證 (read your own write guarantee)
        
        ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/f8de2822-3398-41de-9ff2-8e3ce2197ae9/Untitled.png)
        
        - 您可能會寫入一個節點，然後從節點 B 讀取，而節點 B 尚未收到您的寫入（因為是非同步的）。
        - 如何解決？
            - 寫入後，從主動節點讀取。
                - 實作？
                - 您可以使用時間戳來知道您剛才寫入了，並且在一分鐘內，您的讀取會從主動節點獲取。
                - 或者您只從收到比您的寫入時間戳更新的時間戳的被動節點讀取。
        - 「讀取您自己的寫入保證」在跨設備時，例如您在 PC 上寫入並從 iPhone 讀取？
            - 這可能會出現問題，因為您的 PC 使用 ISDN 而您的 iPhone 使用 5G，它們可能會被路由到不同的資料中心，並使用不同的節點。
                - 您需要在一個中央位置儲存所有中繼資料 (meta-data)，該位置知道這是同一個使用者，以確保「讀取您自己的寫入保證」。
    - 單調讀取保證 (Monotonic reads guarantee)
        - 避免時間旅行到舊時間的異常情況。
        - 您更新了評論，該資料進入節點 A，然後您再次刷新，但這次您訪問了節點 B 上的資料。
        - 然而，節點 B 尚未複寫您的更新，您看到您的評論是舊的。
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/731815bb-57bb-471f-a9fe-8406dc949e4d/Untitled.png)
            
            - 解決方案：如果讀取者曾經寫入，則將其路由到同一個節點。
    - 一致性前綴讀取保證 (Consistent Prefix Read guarantee)
        - 因果關係的違反。
        - A 先生問：「你的年齡是多少？」 (這去了節點 A 並複寫到 NodeA1)。
        - B 先生回答：「20」 (這去了節點 B 並複寫到 NodeB1)。
        - 由於非同步，節點 A1 比 NodeB1 **更晚**更新。
        - 所以，C 先生先看到「20」，然後才看到「你的年齡是多少？」
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/fbca2cb5-968e-41dc-9990-4311a8de61c2/Untitled.png)
            
            - 原因是因為兩個訊息複寫到了不同的節點 $i, j$，
            - 且第二個訊息複寫到 C 所看到的節點 $i$ 和 $j$ 的速度比第一個訊息慢。
        - 某些演算法可以解決這個問題。
    
- 多領導者複寫 (multi-leader replication)
    - 處理起來更複雜，所以主要用於多資料中心案例。
    - 與單領導者相比：
        - 在單領導者中，所有複寫都全局發生，在多領導者中，您可以在每個資料中心有一個領導者，因此複寫發生在這個資料中心內，這可能更快，然後再非同步到其他資料中心。
        - 在單領導者中，故障轉移需要從其他資料中心的被動節點中提升。在多領導者中，每個資料中心彼此獨立。
        - 資料中心內部，網路可能使用更好的私人高速網路而不是 WWW。
    - 離線用戶 (offline-client) 也是多領導者的案例。
        - 像您的郵件和日曆，您編輯後，只有在您重新上線時才會更新到伺服器（另一個領導者）。
        - 所以每個裝置都充當一個領導者資料庫。
        - 範例 CouchDB。
    - 協同編輯 (Collaborative-editing)，如 Google 文件、Wiki。
        - 在這種情況下您不能使用單領導者，您不能使用鎖只允許一個人編輯。
        - 如何處理衝突？
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/50faafd-440c-4fca-899b-7c02e201a971/Untitled.png)
            
            - 從一開始就避免：將一塊資料始終保留在同一個領導者上，以避免在不同領導者中有多個資料副本 $\rightarrow$ 之後很難解決。
            - 如果多個人編輯同一塊資料，我們可以使用最後寫入獲勝 (Last Write Win)，這對您的應用程式來說可能不是一個好情況，因為您會丟失資料。
            - 我們可以嘗試合併，像 B/C，並向讀者展示兩者，讓讀者決定如何合併（在我們下次讀取時合併，或在資料庫偵測到寫入衝突時合併）。
        - 多領導者拓撲：環狀 (circular)、星狀 (star) 和全互連 (all-to-all)。
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/dd17e73f-3f9b-4e4f-93b0-d14b393b52b0/Untitled.png)
            
            - 環狀和星狀 $\rightarrow$ 缺點：在逐一複寫資訊時，需要處理其中一個點失敗的情況，需要標記哪些節點已經複寫（以避免無限迴圈）。
            - 大多數情況下我們使用全互連。
        - 複寫延遲問題也會出現，例如因果關係的違反。
        - 下圖顯示領導者 2 先收到值 2 的寫入，然後是值 1 的寫入。

        - 使用版本向量 (version vectors)（稍後查看）。

- 無領導者複寫 (leader-less replication)
    - 沒有領導者，我們需要一個協調者來進行協調。
    - 稱為 Dynamo 風格（與 AWS 中的 DynamoDB 不同），例如 Riak、Cassandra、Voldemort。
    - 假設客戶端 A 寫入 3 個節點 a、b、c。c 當機，只要有兩個節點 (a, b) 回應 OK，寫入就算成功。片刻之後，c 恢復上線，當客戶端 B 想讀取時，B 如何知道哪個是正確的。我們將使用版本 (version) 來控制。節點 a、b 獲得了較新的版本，因此客戶端 B 知道節點 a、b 是正確的。
        
        ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/9ed19b4d-cdbd-45ce-97dc-5a8eefb5ea66/Untitled.png)
        
        - 如何修復節點 c？
            - 讀取修復 (read-repair)：當客戶端 B 讀取 c 時，用較新的版本值修復節點 c。
            - 反熵 (anti-entropy)：運行背景程序來對齊節點 c。
    - 在上述情況中，我們使用 2 個節點可以計算成功讀取，為什麼是 2 個？
        - $w+r > n$（$w$ 是成功寫入次數，$r$ 是成功讀取次數，$n$ 是節點數）。
        - $w$ 是法定寫入 (quorum write)，$r$ 是法定讀取 (quorum read)。附註：法定人數 (quorum)。
        - 您配置 $w$、$r$、$n$。
        - 下面的情況是 $n=5$，$r=3$，$w=3$，我們可以容忍 2 個失敗。
        - 通常，我們使用 $w = r = (n+1)/2$ 來最大化容忍的失敗節點數。
        - 您甚至可以使用 $w + r \le n$，但您更容易讀取到過時的資料。
        
        ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/50dfe003-2bb8-4741-8701-61ead876e63a/Untitled.png)
        
    - 偵測並行寫入
        - 當客戶端 A 發送到節點 1, 2, 3，而客戶端 B 也發送到節點 1, 2, 3，但節點 1 在客戶端 B 發送時當機。結果，我們在節點之間產生了衝突。
            
            ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/8481b86c-3219-4739-9a52-236dc2ee268d/Untitled.png)
            
        - 如前所述，我們可以使用最後寫入獲勝，但犧牲了持久性。
    - 什麼是並行寫入和先於發生 (happened-before)？
        - 只要兩個寫入操作彼此不知道 $\rightarrow$ 它們就是並行的。
        - 如果寫入 A 依賴於 B $\rightarrow$ 它們具有先於發生關係，反之亦然。
    - 使用版本來處理：每次寫入都會有其版本，伺服器會保留它，當客戶端讀取時，客戶端需要將它們合併在一起。（對於刪除，我們使用墓碑標記 (tombstone mark)）（見下圖）。
        
        ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/48288315-e5fb-4f13-b5cb-5da33e1fef64/Untitled.png)
        
    - 如果我們有很多複本，我們需要追蹤它們的版本 $\rightarrow$ 版本向量 (version vector)。
