# 數據庫發展史簡報：從打孔卡到關係模型的演進

## 執行摘要

本簡報綜合分析了數據庫技術從早期儲存媒介到現代關係模型出現的關鍵發展歷程。核心觀點指出，數據庫的演進並非一蹴可幾，而是由硬體技術的突破與數據管理思想的革新共同推動的。

關鍵要點包括：

1. **硬體決定架構：** 在數據庫系統出現之前，數據的組織形式完全受限於儲存媒介。從僅支援順序訪問的打孔卡和磁帶，到實現革命性隨機訪問的磁盤，硬體的進步為複雜數據模型的誕生奠定了基礎。
2. **前關係型模型的探索：** 隨著磁盤的出現，層次模型（以 IBM 的 IMS 為代表）與網狀模型應運而生。這兩種模型透過物理指針實現了高效的數據訪問，但在結構上過於僵化，將應用程式邏輯與物理儲存緊密耦合。開發者需要編寫「導航式」查詢，明確指出「如何」找到數據，這導致系統靈活性差且維護成本極高。
3. **關係模型的典範轉移：** 1970年，IBM 研究員埃德加·科德（Edgar Codd）提出的關係模型徹底改變了數據庫領域。其核心思想是使用簡單的二維表格來組織數據，並透過「聲明式」查詢語言（最終演變為 SQL）讓使用者只需說明「需要什麼」數據，而無需關心底層的存取路徑。這種邏輯與物理儲存的分離，即「數據獨立性」，極大地提升了開發效率與系統的靈活性，並直接催生了 Oracle 等商業數據庫的誕生，開啟了數據庫工業化的黃金時代。

## 1. 早期數據儲存媒介的局限性

在數據庫概念成形之前，數據的儲存與組織形式完全取決於當時的硬體技術。不同的儲存媒介不僅決定了容量和速度，更直接限制了數據的處理方式。磁盤的出現因其支持隨機訪問的特性，成為數據庫系統誕生的關鍵硬體基礎。

|   |   |   |   |   |
|---|---|---|---|---|
|媒介|活躍時代|關鍵特徵|優點|缺點|
|**打孔卡 (Punched Card)**|20世紀中期|每張卡片儲存80個字符，用於儲存數據與程式碼。|-|容量極小、僅支援順序處理、操作緩慢且依賴人工、易損壞、體積龐大。|
|**磁鼓 (Magnetic Drum)**|1940年代後期 - 1950年代|旋轉的金屬圓柱，表面覆蓋磁性材料。|**支援隨機訪問**，比打孔卡和磁帶更靈活。|體積大、成本高、儲存密度低、讀寫速度受物理旋轉限制。|
|**磁帶 (Magnetic Tape)**|1950年代 - 1960年代|類似錄音帶，數據順序寫入。|容量大（百萬字符級別）、成本低，適合批次處理。|**僅支援順序訪問**，查找效率極低，機械延遲明顯，易磨損。|
|**磁盤 (Magnetic Disk)**|1956年首次出現|由多張高速旋轉的磁性盤片組成，讀寫頭可直接定位。|**革命性的隨機訪問能力**，訪問效率大幅提升，容量巨大（初代已有5MB）。|早期設備體積龐大（如兩台冰箱）、重量驚人（近一噸）、尋道時間長。|

## 2. 前關係型數據庫模型：導航式訪問的興起與挑戰

磁盤帶來的隨機訪問能力，使得構建複雜的數據庫系統成為可能。在1960年代，兩種主流的數據模型——層次模型和網狀模型——應運而生。它們的共同特點是依賴物理指針進行「導航式」查詢，開發者必須在程式碼中明確定義數據的存取路徑。

### 2.1 層次模型 (Hierarchical Model)

- **背景與代表：** 為滿足美國阿波羅登月計畫管理數百萬零件的複雜需求，IBM 於1966年開發了 **IMS (Information Management System)**。
- **核心結構：**
    - 數據被組織成一棵樹狀結構，類似電腦的檔案系統。
    - 節點之間是嚴格的父子關係：一個父節點可以有多個子節點，但一個子節點只能隸屬於一個父節點（一對多關係）。
- **優點：**
    - 沿著固定的指針路徑訪問，查詢速度非常快。
- **缺點：**
    - **結構僵化：** 難以表達複雜的多對多關聯。
    - **查詢複雜：** 跨分支的查詢非常困難，必須手動「導航」。
    - **數據冗餘：** 相同的數據可能出現在不同分支，導致更新異常。
    - **維護成本高：** 一旦層次結構調整，所有相關的應用程式都需要修改。

### 2.2 網狀模型 (Network Model)

- **背景與代表：** 在1960年代與層次模型同期發展，代表性系統是 **IDS (Integrated Data Store)**。
- **核心結構：**
    - 數據結構更像一張有向圖，記錄之間透過指針網絡連接。
    - 原生支援多對多關係：一條記錄可以同時隸屬於多個集合（Set），突破了層次模型的限制。
- **關鍵人物：** 查爾斯·巴赫曼（Charles Bachman）因其在網狀數據庫和標準化方面的貢獻，於1973年成為數據庫領域首位圖靈獎得主。他首次提出了「數據獨立性」的思想。
- **優點：**
    - 能支援比層次模型更複雜的數據關係。
    - 在當時展現出良好的性能。
- **缺點：**
    - **查詢方式仍為導航式：** 程式員必須明確編寫「如何找到數據」的過程，而非「需要什麼數據」。
    - **邏輯與物理強耦合：** 應用程式依然依賴底層的指針結構，一旦結構變更，應用程式也需修改，靈活性不足。

## 3. 關係模型的誕生：一場典範轉移

1970年，數據庫發展迎來了決定性的轉折點。IBM 研究員埃德加·科德在其論文《大型共享數據庫的關係數據模型》中，正式提出了關係模型，為數據庫領域帶來了一場徹底的革命。

### 3.1 核心思想與根本性突破

- **核心思想：**
    - **數據以表格表示：** 所有數據都以簡單的二維表格（關係）形式出現，每一行代表一條記錄，每一列代表一個欄位。
    - **關係連接表格：** 表格之間透過主鍵和外鍵建立邏輯聯繫。
- **根本性突破：聲明式查詢與數據獨立性**
    - **告別導航：** 關係模型引入了「聲明式查詢語言」，使用者只需描述**需要什麼數據**，而數據庫系統則負責規劃如何找到這些數據。這與層次和網狀模型的「導航式」查詢（描述**如何找到數據**）有著本質區別。
    - **邏輯與物理分離：** 開發者無需關心數據在磁盤上的具體儲存方式或指針路徑。這種數據獨立性極大地提升了靈活性，當底層儲存變更時，應用程式無需修改。
- **帶來的優勢：**
    - **靈活性顯著提升：** 數據結構的調整對應用的影響降到最低。
    - **開發效率提高：** 查詢語句（如SQL）清晰易懂，開發者能更專注於業務邏輯。
    - **數據一致性：** 數據的更新和維護更加簡單一致。

### 3.2 從理論到主流：商業化的進程

儘管關係模型具有革命性，但其最初並未被廣泛接受，甚至在IBM內部也受到其成功的IMS產品線的阻力。

- **理論驗證：**
    - **1973年，加州大學伯克利分校**啟動 **Ingres** 項目（PostgreSQL 的前身）。
    - **1974年，IBM** 啟動 **System R** 項目來驗證關係模型，並在此過程中設計了 **SEQUEL** 語言，這就是後來成為業界標準的 **SQL**。
- **商業化浪潮：**
    - **1977年**，一位名叫拉里·埃里森（Larry Ellison）的年輕人，受到科德論文的啟發，看到了其中的巨大商機。他與同事共同出資2000美元成立了一家公司，這就是後來的 **Oracle**。
- **深遠影響：** 關係模型的提出與成功商業化，使數據庫真正走向主流，並開啟了其工業化的進程，為今天我們所熟知的數據驅動世界奠定了基礎。
