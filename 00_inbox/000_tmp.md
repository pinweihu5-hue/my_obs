## 1. 挑戰：Docker 在大規模應用下的瓶頸

### Anthropic 的初始狀況

在專案初期，Anthropic 採用了業界標準工具，包括 Python、Kubernetes 和 Docker。然而，其工作流程圍繞一個單一、巨大的 Docker 映像檔，引發了嚴重的效能問題：

- **巨大的映像檔尺寸**: 
- 35GB。
- 這主要是由於機器學習函式庫為不同硬體加速器架構生成的大量核心
- 研究人員添加後未移除的一次性工具，以及建置過程中的低效率所致。
- **漫長的處理時間**:
    - **拉取時間**: 拉取任何內容都需要約 4 分鐘。
    - **重建時間**: 映像檔的完整重建時間接近一小時。
- **手動協調流程**: 由於重建速度過慢，CI/CD 流程無法自動化，團隊必須手動協調由誰來執行下一次建置。
- **迫切的業務需求**: 一個新的高優先級專案需要開發編譯軟體，開發人員每天需要多次變更和重建，現有的 Docker 流程完全無法滿足此需求。

### Docker/OCI 格式的內在限制

Docker 的核心問題源於其檔案格式和工作流程的內在設計，這些設計在規模化時變得難以擴展：

- **缺乏抽象化**: 除了父映像檔，Dockerfiles 幾乎沒有提供有效的抽象機制。在多個 Dockerfiles 中複製貼上數十行腳本以執行單一概念性操作是很常見的。
- **分層結構效率低下**:
    - **線性依賴**: Docker 的分層是線性的，任何一層的變更都會使其後續所有層級失效並需要重建。
    - **不均衡的層大小**: 映像檔的層大小分佈呈對數關係，通常由一兩個非常「肥胖」的層（例如包含 CUDA 的層）主導。這意味著即使是位於這些大層之前的一個小設定檔變更，也會觸發數十 GB 的資料重建。
- **平行處理能力有限**: 雖然多階段建置（multi-stage builds）提供了一定的平行能力，但操作起來十分笨拙。此外，傳統的套件管理器（如 `apt-get`）的設計使得平行安裝變得困難。
- `**containerd**` **的瓶頸**: Docker 的執行階段核心 `containerd` 在拉取映像檔時雖然可以平行下載各個層，但在解壓縮階段卻是**序列化**的，一次只能處理一個層。這個設計瓶頸對於需要快速啟動大量 Pod 的場景是致命的。
- **OCI 映像檔限制**: 標準化的 OCI 映像檔格式限制每個映像檔最多只能有 128 個層。對於一個 35GB 的映像檔，即使層大小完全平均分配，每層也至少有 250MB，任何微小變更都會導致巨大的下載和快取讀寫開銷。

## 2. 解決方案的演進：擁抱 Nix

面對 Docker 的局限性，團隊選擇了 Nix 作為替代方案，主要看重其根本性的設計優勢。

### Nix 的核心優勢

- **優越的抽象化**: Nix 允許輕鬆組合不同的工具集，例如將建置工具、互動式 Shell 工具和生產環境工具分離並按需組合。
- **細粒度的依賴管理**: 與 Docker 的粗粒度層不同，Nix 將每個軟體包或元件視為一個獨立的「derivation」。這意味著只有真正變更的部分及其直接依賴項需要重建。
- **內建平行處理**: Nix 的設計原生支援平行處理，無論是在單次建置內部、跨不同建置，還是在從快取中拉取或上傳時。
- **精確的依賴追蹤**: Nix 嚴格區分**建置時依賴**（如 LLVM、Clang）和**執行時依賴**。這確保了生產環境中只包含必要的執行時元件，不會混入龐大的建置工具。
- **無限的組合性**: Nix 的 derivation 數量沒有 128 層的限制，一個系統可以輕鬆擁有數千甚至數萬個 derivations。

### 初步實施：無映像檔部署

團隊的第一步是完全繞過 Docker 映像檔的建置過程。

1. **使用 Nix 建置**: 開發人員在本地或 CI 中使用 Nix 建置軟體。
2. **上傳至 Nix 儲存區**: 建置產物被上傳到一個內部共享的 Nix 儲存區（基於 S3 等物件儲存），而不是打包成 Docker 映像檔。
3. **執行時拉取**: 在 Kubernetes Pod 的定義中，不包含完整的應用程式，而是包含一個指向 Nix 儲存區中特定路徑的**參考**。
4. **動態載入**: 當 Pod 啟動時，它首先會是一個輕量級的容器，然後在啟動腳本中從 Nix 儲存區下載所需的 Nix derivations，並將其路徑添加到 `PATH` 環境變數中，最後啟動主應用程式。

為了優化拉取效能，該架構包含了多層快取：

- **中央物件儲存**: 作為主要的 Nix 儲存區。
- **區域性副本**: 自動將資料複製到各個雲端區域的 S3 儲存桶，以避免緩慢的跨區域讀取。
- **區域性快取服務**: 在每個區域部署快取服務，以加速元資料操作並最大化頻寬利用率。

### 初步成果與新問題

這一方案取得了顯著的成功。對於一個約 11GB 的軟體套件：

- **Docker 預估拉取時間**: 約 70 秒。
- **Nix 單一 S3 儲存區**: 降至 45 秒。
- **Nix 加上區域性快取**: 進一步降至 **15 秒**。

然而，這個方案引發了一個新問題：**缺乏節點層級的快取**。Docker 的一個優勢是，如果一個節點上已經存在某個映像檔，再次啟動使用該映像檔的容器時拉取時間為 0。但在當時的 Nix 方案中，每個 Pod 啟動時都會重新從遠端快取下載所有依賴，即使同一個節點上剛剛執行過完全相同的任務。這不僅浪費了 15 秒的啟動時間，更嚴重的是造成了巨大的網路頻寬消耗，可能引發雲端供應商的注意。解決方案顯然是：「不要丟棄下載的資料」。

## 3. 尋求持久化快取：評估不同方案

為了在節點上保留已下載的 Nix derivations，團隊評估了社群中已有的解決方案，並根據自身需求進行了權衡。

**核心需求:**

- **生產環境**: `/nix/store` 應為唯讀，以確保穩定性。
- **開發環境**: `/nix/store` 需為可讀寫，以便開發人員能動態安裝調試工具。同時，Nix 資料庫必須存在且可更新。

### 方案一：Nix 分層儲存 (Nix Layered Store)

此方案是 Nix 的一個實驗性功能，它允許將多個 Nix 儲存區合併為一個邏輯視圖（一個位於容器內可讀寫的上層儲存區，一個位於主機上唯讀的下層儲存區）。

- **否決原因 1 (特異性)**: 此方案會將主機下層儲存區中的**所有**快取內容都暴露給容器。這可能導致開發人員無意中依賴了某個恰好存在於節點上的未宣告路徑（例如 `jemalloc`），導致其應用在本地可以執行，但在一個沒有快取該路徑的生產節點上失敗。團隊需要確保只有明確宣告的依賴項在容器中可用。
- **否決原因 2 (垃圾回收)**: 該方案**不支援**對下層儲存區（即節點上的快取）進行垃圾回收。對於需要嚴格管理節點 SSD 使用率的 Anthropic 來說，這是一個致命缺陷。

### 方案二：Nix Snapshot

這是一個由 Tweag/PD Partners 開發的開源工具，被認為是當時業界最先進的解決方案。它作為 `containerd` 的一個外掛程式運作。

- **運作方式**: 當 Kubernetes 請求 `containerd` 啟動一個帶有 Nix 依賴參考的映像檔時，`containerd` 會呼叫 Nix Snapshot 外掛程式。後者負責從遠端下載 Nix 路徑到節點上，並使用繫結掛載（bind mounts）將**特定**的路徑掛載到容器的檔案系統中。
- **優點**: 它完美地解決了 Nix Layered Store 的兩個問題：
    - **特異性**: 只掛載請求的路徑。
    - **垃圾回收**: 透過與 `containerd` 的生命週期掛鉤，可以安全地進行垃圾回收。
- **否決原因 1 (部署限制)**: Anthropic 使用的多個雲端服務供應商不允許或難以客製化其 `containerd` 的配置，因此無法部署 Nix Snapshot。
- **否決原因 2 (維運開銷)**: 團隊傾向於避免在每個節點上執行一個常駐的 Nix 守護程序（Daemon），尤其是在非 NixOS 的 AMI 上管理和更新這樣的服務會非常痛苦。

## 4. 最終方案：Nix Sidecar

由於現有方案均不適用，團隊決定自行開發一個解決方案，其核心理念是**「使用者空間的 Nix Snapshot」**，在不修改底層基礎設施的前提下實現相同的功能。

### 運作流程

Nix Sidecar 作為一個 Kubernetes `init` 容器和 `sidecar` 容器運作：

1. **啟動**: 當一個 Pod 啟動時，Nix Sidecar 容器先於主應用程式容器啟動。
2. **掛載**: Nix Sidecar 會掛載兩個關鍵磁碟區：
    - 一個來自**主機 SSD** 的路徑，用於持久化儲存 Nix derivations。
    - 一個名為 `nix-container` 的**空磁碟區**，此磁碟區將與主應用程式容器共享。
3. **下載與快取**: Sidecar 檢查工作負載所需的 Nix 儲存路徑，並從遠端 Nix 儲存區將它們下載到主機 SSD 的掛載點上。
4. **繫結掛載**: Sidecar 使用繫結掛載，將**僅僅**是本次任務所需的 Nix 路徑（例如 20 個）從主機 SSD 上的完整快取（可能有 100 個路徑）掛載到共享的 `nix-container` 磁碟區中。
5. **準備環境**: 如果是開發工作負載，Sidecar 還會設定 Nix 資料庫並確保檔案系統是可讀寫的。
6. **啟動主應用**: 此時，主應用程式容器啟動。對它而言，它看到的是一個已經準備好的、包含所有所需依賴的 `/nix/store` 檔案系統。
7. **持續運作與清理**: Nix Sidecar 會繼續在背景執行，以低優先級清理舊的、不再使用的 Nix 路徑（垃圾回收），並在 Pod 終止時負責卸載所有繫結掛載，以防 Pod 卡在 `Terminating` 狀態。

### 技術細節與權衡

- **掛載傳播 (Mount Propagation)**: 為了讓在 Sidecar 容器內建立的繫結掛載對主容器可見，必須在 Kubernetes 中啟用此功能。
- **特權容器**: 執行繫結掛載需要容器以特權模式執行。由於 Nix Sidecar 的程式碼非常簡單（約 50 行 Bash 腳本），且不執行任何用戶控制的程式碼，安全風險被認為是可控的。
- **Sidecar 生命週期**: 使用 Kubernetes 的 sidecar 功能（而不是傳統的 `init` 容器）至關重要，以確保在主容器結束後，Sidecar 仍能執行清理操作。

## 5. 成果與結論

### 性能指標

部署 Nix Sidecar 後，拉取時間的分佈圖顯示：

- **絕大多數**的拉取時間集中在 **0 秒**，這表示快取命中。
- 圖中仍有一些較小的峰值，對應於在新節點上的首次完整下載或部分下載。
- 該工具仍在持續開發和優化中。

### 核心啟示

- **Docker 並非萬能**: 儘管 Docker 是業界標準且非常出色，但其內在的格式限制在規模化應用中會成為嚴重的效能瓶頸。
- **Nix 是解放的工具**: Nix 提供了擺脫這些束縛的強大能力，讓使用者能夠建構更高效、更可靠的系統。
- **客製化是必要的**: 直接使用 Nix 並不能解決所有問題。成功的關鍵在於理解其「第一性原理」，並圍繞這些原理建構符合自身需求的工具鏈（即「自己動手組裝」）。
- **自建方案的成功**: 透過自行開發 Nix Sidecar，Anthropic 成功地在規模化環境中實現了高效的部署體驗。

**引述**: 「Nix Sidecar 是一個內部專案，但好消息是它只有大約 200 行程式碼……關鍵是理解腦中的所有技術和宏觀藍圖。一旦你有了這個藍圖，自己動手實現其實相當快。」
