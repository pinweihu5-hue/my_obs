- 我們將討論：網路問題、時鐘問題和程序暫停 (process pause)。
- 單機 vs. 分散式 (dist)
    - 當您在單機上運行軟體時，它通常是成功運行或根本不運行，通常沒有「部分成功」的情況。
    - 在單機上，您可以運行該程序，或者不能運行，我們稱之為**確定性 (deterministic)**。
    - 在分散式系統中，我們會遇到**部分故障 (partial failure)**，而且我們不知道它在哪裡失敗，它是**非確定性 (nondeterministic)** 的。
    - 如果您的網路出現問題，回應只是沒有回覆，您不知道它是失敗了還是沒有，因為您無法預測它應該多久返回（因為回應沒有回覆有很多種方式，因此您不知道如何估計它） $\rightarrow$ 本質上是非確定性的。
    - 部分故障和非確定性使分散式系統變得困難。
- 雲端運算和超級運算 (cloud computing and super computing)
    - 在一個光譜上，我們有 HPC（高性能計算），數千個 CPU 用於運行 CPU 密集型任務，例如分子動力學或天氣預報。
    - 在另一個光譜上，我們有雲端運算，使用許多資料中心和乙太網路，並根據需求 (on demand) 擴展。
- 不可靠的網路 (unreliable network)
    - 網際網路、資料中心，大多數網路以**非同步**方式運行（非同步封包系統）。
    - 非同步，意味著它會發送，而您不確定它何時會到達。
    - 以下是您的請求發送並遇到問題時的可能情況：
        - 您的請求只是丟失了（有人拔掉了您的線纜或電源中斷）。
        - 請求在佇列中等待（網路負載高）。
        - 節點當機/關閉。
        - 節點暫時停止（見下文程序暫停），例如它正在運行 GC（垃圾回收）。
        - 節點已處理請求，但在發送回覆時丟失（例如網路交換器出現問題）。
        - 節點已處理請求，但在當下，沒有丟失，只是在回傳佇列中等待。
    - 簡單來說，我們可以分為三種情況：請求未到達節點、節點當機、回應丟失。

        - 通常我們使用**超時 (timeout)** 來處理這個問題，如果超時，我們就知道它失敗了，我們可能會重試並確保請求是**冪等性 (idempotent)** 的。
    - 偵測故障 (detect failure)
        - 許多系統會自動偵測故障，例如：
        - 負載平衡器 (load balance) 會檢查並將節點移出輪替 (rotation)。
        - 主動/被動複寫資料庫 $\rightarrow$ 如果主動節點失敗，它會自動提升被動節點。
        - 儘管如此，很難知道哪個節點發生故障，只有在某些情況下我們可能知道：
            - 如果您可以連線到該節點，並且沒有程序在監聽該連接埠（程序可能當機），您可能會收到回覆，也可能不會。
        - 無論如何，您可能會從某些層級（應用程式層、TCP 層、路由器層）收到錯誤，或者根本沒有錯誤。
        - 您能做的唯一方法就是重試，如果所有重試都超時，您就知道出了問題。
    - 超時和**無界延遲 (unbounded delay)**
        - 我們如何設定超時？ $\rightarrow$ 沒有明確的答案。
            - 設定太低，它可能只是處理時間過長，您就認為它死了並重試。
                - 重試或發送到其他節點，只會給您的系統增加更多負載，這會使系統更不穩定，稱為**級聯故障 (cascading failure)**。
            - 兩個參數：
                - $d$：資料需要傳遞的最大時間。
                - $r$：節點處理請求的最大時間。
                - $2d+r$ $\rightarrow$ 您需要獲得回應的時間，否則您可以重試或做其他事情。
        - 網路擁塞和佇列 (network congestion and queueing)
            - 當您在網際網路上發送請求時，會發生許多佇列。
            - 假設許多節點試圖將封包發送到同一個目的地，網路交換器會將它們佇列起來。
                
                ![Untitled](https://s3-us-west-2.amazonaws.com/secure.notion-static.com/551f67ac-468b-47eb-a89e-06fe388d0c95/Untitled.png)
                
            - 即使封包到達節點，如果節點中的 CPU 很忙，作業系統 (OS) 也會將傳入的網路請求放入佇列中等待，直到 CPU 可用。
            - 在虛擬環境中，運行的 OS 有時會暫停 $1x$ 毫秒以等待其他 OS 使用 CPU，在這 $1x$ 毫秒內，待處理的虛擬機器 OS 無法從網路消耗請求，因此傳入的請求也需要等待。
            - TCP 有自己的流量控制，稱為擁塞避免/反壓 (congestion avoidance / backpressure) 來控制流速以避免過載。這是在資料甚至進入網路之前，在發送方增加的額外佇列。
            - TCP vs UDP：
                - 這是可靠性和延遲變異性之間的權衡。
                - VoIP 使用 UDP，它不使用流量控制，也不會重新傳輸丟失的封包。
                - 當延遲的資料沒有價值時（例如，重新發送 VoIP 期間丟失的聲音可能不值得或不直觀），UDP 是一個不錯的選擇。
                - 重試發生在人類層級：您可以再說一次嗎？
            - 以上所有情況都會導致網路故障/延遲變異性。
            - 您只需要不斷實驗，衡量往返時間需要多長，節點分佈、您的應用程式特性，並考慮故障偵測延遲與過早超時風險之間的權衡。
