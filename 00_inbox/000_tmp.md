## DDIA encoding and evolution

- 當我們討論資料綱要演變 (data schema evolution) 時，我們會關注**相容性 (compatible)**：
    - **向後相容 (Backward Compatible)**
        - 較新的程式碼可以讀取由較舊程式碼寫入的資料。
        - 新程式碼可以處理**舊程式碼寫入的資料**。
        - 通常不難實現，因為您已經知道舊程式碼的資料格式，可以進行處理（或者說只是處理難易度的問題）。
    - **向前相容 (Forward Compatible)**
        - 較舊的程式碼可以讀取由較新程式碼寫入的資料。
        - 舊程式碼可以處理**新程式碼寫入的資料**。
        - 這比較棘手，因為它要求舊程式碼能夠忽略新程式碼新增的內容。
    - 不同的綱要使用不同的方式來支援新舊程式碼的共存！

- **用於編碼資料的格式 (Formats for encoding data)**
    - **編碼 (Encoding)**
        - 當您需要透過網路傳輸、寫入檔案等時。
        - 將記憶體表示（物件、結構、列表、陣列、雜湊表、樹）轉換為位元組 (byte)。
        - 例如 JavaScript 中的 `JSON.stringify` API。
    - **解碼 (Decode)**
        - 當您需要讀取檔案或從網路接收資料時。
        - 例如 JavaScript 中的 `JSON.parse` API。
    - **術語：**
        - 編碼 (encoding)、**序列化 (serialization)、封送處理 (marshalling)**
        - 解碼 (decoding)、解析 (parsing)、**反序列化 (deserialization)、解封送處理 (unmarshalling)**
    - **特定語言的格式：**
        - 例如 Java 的 `java.io.Serializable`、Ruby 的 `Marshel` 或 Python 的 `pickle`。
        - 通常不是一個好的選擇：
            - 綁定到特定語言。
            - 為了反序列化，您需要實例化任何類型，這可能帶來**安全問題**。
            - 有時，這些函式庫不管理版本。
            - 有時，這些函式庫的效能不佳。
    - **JSON、XML 和 CSV**
        - JSON 和 XML 是最受歡迎的，但如今 JSON 比 XML 更受歡迎，因為：
            - XML 內容過於冗長 (verbose)，且不必要的複雜。
            - CSV 也是一種編碼方式，但由於網頁瀏覽器支援等因素，JSON 仍然是主要使用的格式。
        - JSON、XML、CSV 都是人類可讀的純文字，易於閱讀，但：
            - 編碼會留下一些**歧義 (ambiguity)**：
                - XML 和 CSV 無法區分數字和字串（除非使用綱要工具檢查）。
                - JSON 無法區分浮點數和整數，對於數字沒有足夠的精度，當數字大於 $2^{53}$ 時可能會出現問題。
            - JSON 和 XML 對 Unicode 支援良好，但**不支援二進位字串 (binary-string)**，除非使用 Base64 或相關方式編碼，但這會使其大小增加 1/3。
            - XML 和 JSON 都有綱要支援，但學習不易，許多人懶得使用。
        - 儘管如此，XML、JSON 和 CSV 仍然被大量使用，足以應對許多使用案例，只需要確保在組織內部使用標準化的方式即可。
    - **二進位格式 (Binary format)**
        - JSON 有其二進位格式（MessagePack、BSON、BJSON、UBJSON、BISON 和 Smile），XML 也有（WBXML 和 Fast Infoset），但它們不像純文字版本那樣被廣泛使用。
        - **範例：**
            ```json
            {
                "userName": "Martin",
                "favoriteNumber": 1337,
                "interests": ["daydreaming", "hacking"]
            }
            ```
            - MessagePack 二進位格式為 66 位元組，而純文字為 88 位元組。
        - **Apache Thrift (FB)、Protocol Buffers (Google)**，概念相同。
        - 兩者都需要**綱要 (schema)** 來編碼資料。
        - 使用 Thrift 的 **IDL (介面定義語言)** 來描述綱要：
            ```json
            struct Person {
                1: required string       userName,
                2: optional i64          favoriteNumber,
                3: optional list<string> interests
            }
            ```
            類似於以下的 Protocol Buffers 綱要：
            ```json
            message Person {
                required string user_name       = 1;
                optional int64  favorite_number = 2;
                repeated string interests       = 3;
            }
            ```
            由於我們有這些綱要資訊，可以在其編碼的二進位格式中節省一些位元組：
            - Thrift Binary Protocol：59 位元組
            - Thrift CompactProtocol：34 位元組
            - Protocol Buffer：33 位元組
        - **綱要演變 (Evolution of Schema)**
            - 如何處理變更？
            - 您**不能**更改綱要中的**欄位標籤 (field tag)**。
            - 但您可以更改欄位名稱。
            - **向後相容：** 為了讓新程式碼可以讀取舊程式碼寫入的資料，請將新欄位設為 `optional` (可選)。
            - **向前相容：** 為了讓舊程式碼可以讀取新程式碼寫入的資料，無需額外努力，只需新增欄位，舊程式碼會自動跳過無法識別的新欄位。
            - **刪除欄位呢？** 為了保持相容性，您只能刪除 `optional` 的欄位。
        - **Avro**
            - Apache Avro 是另一種二進位編碼格式，是 Hadoop 的一個子專案。
            - 綱要可以透過兩種方式表示：
                - IDL：
                    ```json
                    record Person {
                        string                userName;
                        union { null, long }  favoriteNumber = null;
                        array<string>         interests;
                    }
                    ```
                - JSON：
                    ```json
                    {
                        "type": "record",
                        "name": "Person",
                        "fields": [
                            {"name": "userName", "type": "string"},
                            {"name": "favoriteNumber", "type": ["null", "long"], "default": null},
                            {"name": "interests", "type": {"type": "array", "items": "string"}
                        ] 
                    }
                    ```
                - **請注意，其綱要中沒有欄位標籤！**
                - 其二進位格式的位元組數是目前最小的：32 位元組。
            - **沒有欄位標籤** → 需要「按順序」解析綱要。
            - **寫入者綱要 (writer's schema)** 用於編碼成二進位格式。
            - **讀取者綱要 (reader's schema)** 用於解碼二進位格式。
            - 讀取者綱要和寫入者綱要**不需要相同**，只需要**相容**即可！
            - 如果它們相容，Avro 函式庫會為您進行轉換：
                - 如果讀取者綱要有但寫入者綱要沒有，則使用預設值。
                - 如果寫入者綱要有但讀取者綱要沒有，則跳過。
            - **如何處理演變？**
                - 您可以新增或移除**具有預設值**的欄位。
                - 處理 `null` 的方式不同：在其他協定中 `null` 是一種資料類型，但在 Avro 中，您需要使用 `union`：
                    `union {null，long，string}` → 表示此資料類型可以是 null、long 或 string。
                - 您可以更新類型，Avro 會為您轉換。
                - 更改欄位名稱和向聯合類型新增新類型是**向後相容**但**非向前相容**的，這意味著：
                    - 新程式碼可以處理舊程式碼寫入的資料。
                    - 舊程式碼無法處理新程式碼寫入的資料。
            - **如何知道解碼時要使用哪個綱要？**
                - 對於像 Hadoop 這樣包含許多記錄的大檔案，通常只有一個綱要檔案對應數百萬條記錄。
                - 對於資料庫，您可能有不同時間點、不同版本的記錄 → 為每條記錄新增一個**綱要版本**，並使用單獨的表格來儲存綱要版本。
                - 對於透過網路通訊的兩個程序，他們可以在建立連線時協商版本。
                - 在資料庫中擁有綱要版本總是有益的，可以使用遞增數字或綱要的雜湊值。
            - **Avro 動態生成：**
                - 沒有欄位標籤是設計 Avro 的目標之一，目的是讓 Avro 幫助我們在綱要相容時進行轉換/調整。
            - **關於程式碼生成 (Code Gen)**
                - 程式碼生成意味著，當您定義綱要時，可以透過綱要自動生成程式碼，將應用程式連接起來。
                    - Thrift 和 Protobuf 依賴程式碼生成，這對於靜態語言（如 Java、C、C++）很有好處，有助於靜態類型檢查，並有效利用記憶體。
                - 但對於動態語言（Python、Ruby、JS），程式碼生成提供的益處較少，沒有靜態類型檢查。
                - Avro 提供**可選**的程式碼生成過程，您也可以選擇不進行程式碼生成，無需考慮綱要。
        - **綱要的優勢**
            - 減少資料的位元組數（某些資訊已包含在綱要中）。
            - 綱要本身就是一種文件。
            - 資料庫中有了綱要，您總是知道新舊綱要是否相容。
            - 對於靜態類型語言，綱要可以驅動程式碼生成，進而實現類型檢查。

- **資料流的三種模式 (3 Modes of Dataflow)**
    - **透過資料庫 (Thru database)**
        - 當您寫入資料庫時，需要編碼。
        - 當您從資料庫讀取時，需要解碼。
        - **向後相容**很重要，即較新的程式碼可以讀取由較舊程式碼寫入資料庫的資料。
        - **向前相容**（較舊的程式碼可以讀取由較新程式碼寫入資料庫的資料）在您進行**滾動更新 (rolling update)** 時非常重要。
        - 當您使用不同的綱要寫入資料庫時，請務必小心，您可能會**遺失資料**：
            - 假設您定期使用快照備份資料庫，或將資料傳送到資料倉儲。
            - 通常，即使資料庫包含多個版本的資料綱要，我們也會使用最新的綱要將資料傳送到資料庫。
            - 資料庫的舊綱要無法識別新的資料欄位，會直接跳過它們。
            - 當您從資料庫讀取並更新寫回時，您的資料就會遺失。
        - 如果資料儲存到資料倉儲進行分析，則可能需要考慮使用**欄式儲存 (col-storing)** 以獲得更好的效能。
    - **透過服務呼叫 (Thru service call)**
        - 主要使用**客戶端-伺服器架構**進行通訊。
        - 伺服器提供 API 供呼叫。
        - 提供 API 的伺服器稱為**服務 (service)**。
        - 網頁：客戶端/瀏覽器向網頁伺服器發送請求，例如使用 GET 下載 HTML/CSS/JS 檔案，使用 POST 發送/修改資料，使用雙方約定的格式。
        - 伺服器本身可以是其他伺服器的客戶端。例如，應用程式伺服器是資料庫的客戶端。
        - 一些大型應用程式會將其功能劃分為許多小型服務，我們稱之為**服務導向架構 (SOA)** 或**微服務架構 (microservice architecture)**。
        - 在某種意義上，服務就像資料庫一樣，它們都允許客戶端從中獲取資料，不同之處在於，資料庫提供查詢語言，而服務提供特定的 API 端點。
        - SOA 的關鍵設計目標是使服務在開發上**獨立**：
            - 這使得維護和更新更容易（我只需要部署一個服務，無需擔心其他服務）。
            - 彼此**解耦 (decouple)**。
            - 這也意味著它們需要在其通訊 API 版本上保持**相容性**。
        - 兩種流行的網頁服務：**REST** 和 **SOAP**。
        - **SOAP**
            - 使用 XML 發送網頁請求。
            - 使用 **網頁服務描述語言 (WSDL)**。
            - WSDL 不易於人類閱讀，依賴於工具、IDE、程式碼生成。
            - 透過程式碼生成支援，旨在使**遠端呼叫看起來像本地呼叫**。
            - 適用於靜態語言，如 Java。
            - 如果能利用上述所有優勢，它更像是一個利基解決方案。
            - **為什麼不如 REST 流行？**
                - 儘管有 WSDL 標準，但不同供應商的函式庫仍然存在差異，需要雙方都採用。
                    - REST 不需要這樣，只要雙方都使用 HTTP 即可（HTTP 是每個人都在使用的...）（REST 更高階，是一種基於 HTTP 的通訊設計理念）。
                - XML 更冗長。
                - 動態語言更容易快速啟動專案，而 TypeScript 的興起也有助於 JavaScript 在中大型專案中的採用。
        - **REST**
            - 最受歡迎的。
            - **不是協定**，REST 是一種基於 HTTP 通訊的**設計理念**。
            - 使用簡單的資料格式（純文字）。
            - 使用 `URL` 來表示資源，利用 HTTP 功能進行快取控制、身份驗證等。
            - 較少涉及程式碼生成和工具。
        - **RPC (遠端程序呼叫)**
            - 意圖是使遠端呼叫看起來像本地函數呼叫，但：
                - 本地函數呼叫和遠端呼叫的**失敗**本質上是不同的：
                    - 本地函數呼叫更具可預測性，失敗取決於您的參數設定錯誤或程式碼邏輯。
                    - 遠端呼叫**也**取決於**網路問題**，這是一個完全不同的層面，可能發生許多您無法控制的事情。
                - **關於失敗：**
                    - 本地函數呼叫會拋出錯誤、返回結果或進入無限迴圈。
                    - 遠端呼叫也可能有**逾時 (time-out)**，此時您基本上不知道發生了什麼。
                    - 對於 RPC，如果您想在失敗時再次呼叫函數（重試），您需要考慮這樣做是否可以（是否為**冪等 (indempotent)** 操作？）。
                - **呼叫時間：**
                    - 本地函數呼叫時間大多在給定的可預測時間範圍內。
                    - 遠端呼叫 → 取決於您的網路狀況。
                - **語言：**
                    - 本地函數呼叫在單一語言中。
                    - RPC：輸入和輸出可能使用不同的語言，需要處理。
                        - 例如，將一個大於 $2^{53}$ 的數字從一種語言傳遞給 JavaScript，而 JavaScript 無法處理（需要使用 BigInt 來處理）。
    - **透過非同步訊息傳遞 (Thru async msg passing)**
        - 上述我們討論了 2 個程序之間的通訊：
            - 資料庫 (1 個程序寫入，1 個程序讀取)
            - REST, RPC (1 個程序發送，1 個程序接收)
        - 訊息傳遞是不同的，它有一個**中間人**，稱為**訊息代理 (msg broker) / 訊息佇列 (msg queue) / 訊息導向中介軟體 (msg-oritented middleware)**。
        - **優勢：**
            - 它充當**緩衝區**：例如流量過大或伺服器停機。
                - 如果有佇列，就不用擔心。
                - 如果伺服器停機，訊息會保留在佇列中，只有在訊息成功處理後才會被移除。
            - 如果第一次傳遞失敗，它會為您**重試**訊息傳遞。
            - 客戶端無需知道伺服器，訊息代理/佇列是中間人。
            - 可以將 1 條訊息發送到多個消費者（**扇出/廣播 (fan-out)**）。
            - **解耦**生產者和消費者。
                - 可以切換到不同的單元，例如您可以使用 Lambda、Batch 或其他類型的程序作為消費者或生產者。
        - 它大多是**非同步 (asynchrous)** 的：
            - 意味著 A 發送給 B，B 不需要立即在給定時間內回應。
            - B 可以在稍後的時間處理它（通常意味著 B 從 A 接收了太多，B 需要按照自己的步調處理）。
        - **訊息佇列 (Message Queue)**
            - 過去有 TIBCO、IBM WebSphere 和 webMethods，現在有更多選擇，如 RabbitMQ、ActiveMQ、HornetQ、NATS 和 Apache Kafka 等。
            - 一個程序發送到一個**主題 (topic)**，佇列將確保消費者/訂閱者會收到訊息。
            - 一個佇列可以有多個生產者和消費者。
            - 訊息佇列不限制特定的資料模型，只是一串位元組和一些元資料，只要綱要/編碼/生產者和消費者是解耦的即可。
